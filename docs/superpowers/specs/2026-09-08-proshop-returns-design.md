# Pro-shop returns, managed through enquiries

**Date:** 2026-09-08
**Repos:** OTA (backend, MCP), ota-table-bookings (dashboard)
**Out of scope:** the client website (e.g. willy-t-bvi), Stripe refunds, hotal-ui changes.

## Summary

A guest who bought from a property's shop can ask to return some or all of an order. OTA records the return as a first-class entity with its own status, and opens an enquiry thread for it at the same time, so staff manage the conversation in the existing enquiries view (replies, AI drafts) and change the return's status from inside that thread. The guest always gets a first reply straight away: the AI reply pipeline writes it when it can, and a plain templated acknowledgement goes out when it can't. Refunds stay manual in Stripe for now; a status records that they happened.

Identification is order reference plus the email on the order. OTA has no link to the website's Clerk users and does not need one.

## Decisions taken

| Question | Decision |
|---|---|
| What is a return in OTA? | Its own record with lines and status, plus a linked enquiry. Not a JSON blob on the enquiry. |
| Who raises one? | The guest via the website (reference + email), or staff from the dashboard Orders dialog. |
| Refund handling | None automated. `refunded` is a status staff set after refunding in Stripe. |
| Status flow | `requested → approved → received → refunded`; `rejected` from `requested`; `cancelled` from any state except `refunded`. |
| Multiple returns per item | Allowed. Only cap: total quantity across non-rejected, non-cancelled returns may not exceed the quantity bought. |
| Reason | One free-text reason per return, not per line. |
| Guest emails | One first reply per return (AI, or the fallback acknowledgement). Nothing automatic on later status changes. |
| Dashboard | Managed inside the enquiry reply dialog. No Returns page yet. |

## Data model

Migration `migrate-2026-09-08-proshop-returns.sql`, applied to both local and live, and mirrored in `schema.sql`.

### `proshop_order.reference`

- `VARCHAR(12) NOT NULL`, unique per property (`UNIQUE (property_id, reference)`).
- Six characters from the alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I). Generated in `createOrder`; on a unique-violation retry with a fresh code (bounded, 5 attempts).
- Migration backfills existing rows with the same generator before adding `NOT NULL`.
- Returned on every order response and shown in the dashboard Orders dialog. Websites are expected to show it on their confirmation page and email; that's their change, not this one.

### `proshop_return`

| column | type | notes |
|---|---|---|
| id | UUID PK | |
| property_id | UUID NOT NULL → property | |
| order_id | UUID NOT NULL → proshop_order | |
| event_inquiry_id | UUID NOT NULL → event_inquiry | the thread opened for this return |
| status | VARCHAR(20) NOT NULL DEFAULT 'requested' | CHECK IN ('requested','approved','rejected','received','refunded','cancelled') |
| reason | TEXT | guest's or staff's reason, may be empty |
| raised_by | VARCHAR(10) NOT NULL | 'guest' or 'staff' |
| created_at, updated_at | TIMESTAMPTZ | |

Indexes on `property_id`, `order_id`, `event_inquiry_id`.

### `proshop_return_item`

| column | type | notes |
|---|---|---|
| id | UUID PK | |
| return_id | UUID NOT NULL → proshop_return ON DELETE CASCADE | |
| order_item_id | UUID NOT NULL → proshop_order_item | |
| quantity | INT NOT NULL CHECK (quantity > 0) | |

Index on `return_id` and on `order_item_id` (the cap query).

### `property.return_instructions`

`TEXT`, nullable. Free text staff write once ("Post to …, include your reference, within 30 days"). Used by the AI prompt and the fallback acknowledgement. Read and written via `GET/PUT /api/property/me` alongside the tax fields.

### `event_inquiry`

No schema change. A return's enquiry has `event_type = 'Return order items'`, `event_date NULL`, and `message` generated by OTA (see API). The dashboard's existing feeds show the type badge without a hotal-ui change.

## API

All routes on the existing proshop router, `authenticateOrApiKey`, so a property API key (website) or a Clerk token (dashboard) both work. Swagger updated for each.

### `POST /api/proshop/orders/lookup`

Body: `{ reference, email }`.

- Normalises: reference upper-cased and trimmed; email lower-cased and trimmed, compared case-insensitively against `contact_email`.
- 404 `{ error: 'Order not found' }` on any mismatch, and the same 404 when the order exists but is not `paid`. No hint about which half was wrong.
- 200: the order (id, reference, created_at, status, payment_status, totals, contact_name) and `items[]` each with `id, item_name, unit_price, quantity, returnable_quantity`, where `returnable_quantity = quantity − Σ quantity of proshop_return_item on this line whose return status ∉ ('rejected','cancelled')`.

### `POST /api/proshop/returns`

Body, one of two shapes:

- Guest (website): `{ reference, email, reason?, items: [{ order_item_id, quantity }], branding? }`
- Staff (dashboard, Clerk token only): `{ order_id, reason?, items: [...] }`. An API-key caller sending `order_id` gets 400; the website must go through reference + email.

Validation, in order:

1. Order resolves (same rules as lookup, including `paid`), 404 otherwise.
2. `items` non-empty, each `order_item_id` belongs to that order, each `quantity` a positive integer, no duplicate lines. 400 otherwise.
3. Cap: for each line, `quantity ≤ returnable_quantity` computed inside the transaction with the order row locked (`SELECT … FOR UPDATE` on `proshop_order`) so two concurrent requests can't both pass. 409 with the offending line's name and remaining quantity.
4. `reason` ≤ 2000 chars. `branding` validated with the enquiry's existing validator.

In one transaction:

1. Insert `event_inquiry`: `property_id`, `name = order.contact_name`, `email = order.contact_email`, `phone = order.contact_phone`, `event_type = 'Return order items'`, `branding` if given, `message` generated as:

   ```
   Return request for order <REF>

   2 × Willy T Rash Guard (M)
   1 × Burgee

   Reason: <reason or "(none given)">
   ```
2. Insert `proshop_return` (`raised_by` from which body shape was used) and its lines.
3. Commit.

After commit, outside the transaction:

- `publishNewInquiry` as `createInquiry` does today, so the enquiries feed updates live.
- `runAiReply({ inquiryId, triggerType: 'new_inquiry' })`, then the guaranteed-first-reply check (see Email and AI).

Response 201: the enquiry row with `return` embedded (see Enquiry embedding).

### `GET /api/proshop/returns` and `GET /api/proshop/returns/:id`

List accepts `status`, `order_id`, `cursor`, `limit` (same cursor pattern as orders). Each row carries `reference`, `order_id`, `event_inquiry_id`, `status`, `reason`, `raised_by`, timestamps, and `items[]` with `order_item_id, item_name, unit_price, quantity`. Items fetched with one `ANY($1)` query per page, not per row.

### `PUT /api/proshop/returns/:id`

Body: `{ status }`. Legal transitions:

| from | to |
|---|---|
| requested | approved, rejected, cancelled |
| approved | received, cancelled |
| received | refunded, cancelled |
| refunded | (none) |
| rejected, cancelled | (none) |

Anything else 409 `{ error: "Cannot move a return from 'X' to 'Y'" }`. Unknown status 400.

Side effects:

- Moving to `received` calls the existing `restoreStockForItems` with the return's lines, since the goods are back on the shelf. No other transition touches stock.
- Every successful change publishes `return-status-changed` `{ id, order_id, reference, status }` on `property:<id>:shop-orders`. The current `<live-shop-orders-feed>` only subscribes to named events, so it ignores this until a later hotal-ui release picks it up.
- `updated_at = now()`.

Response 200: the return with items.

### Enquiry embedding

`listInquiries` and the single-enquiry read gain a nullable `return` object via `LEFT JOIN proshop_return pr ON pr.event_inquiry_id = ei.id` and a second `ANY($1)` query for the lines of the returns on the page:

```json
"return": { "id", "order_id", "reference", "status", "reason", "items": [ { "order_item_id", "item_name", "quantity" } ] }
```

`null` for general enquiries. The dashboard needs no extra request to render the panel.

### MCP

Four tools in `mcp-server/tools.js`, thin wrappers over the above: `lookup_proshop_order`, `create_proshop_return` (guest shape only), `list_proshop_returns`, `update_proshop_return_status`.

## Email and AI

### Prompt

In `aiReplies.js`:

- **Cached system prefix.** When `property.return_instructions` is set, add a `<return_instructions>` block after the venue facts. Add one standing sentence to the fixed instructions: on an enquiry that carries a return, confirm what is being returned, relay the return instructions, and never propose a booking.
- **User turn.** When the inquiry has a return, `buildUserMessage` adds inside `<inquiry>`:

  ```
  <return order_reference="WT4F7K" status="requested">
    <line quantity="2">Willy T Rash Guard (M)</line>
    <line quantity="1">Burgee</line>
    <reason>…</reason>
  </return>
  ```
- `loadInquiry` in the pipeline joins the return so it's available without a second query. Booking-on-approval is skipped when the inquiry has a return, regardless of what the model proposes.

### Guaranteed first reply

`createReturn` awaits `runAiReply`, then:

1. If an outbound `event_inquiry_message` now exists for the enquiry (the AI auto-sent), stop.
2. Otherwise send the fallback acknowledgement and insert it as an outbound `event_inquiry_message` recorded the same way an auto-sent draft is (no human sender), so staff see it in the thread and the model reads it next time.

The fallback covers: AI mode `off`, a pending draft awaiting a human, a draft below the auto-send score or flagged `requires_human`, zero tokens (the pipeline has already forwarded the enquiry to `fallback_email`; the guest still gets acknowledged), and model failure.

If a pending draft exists when the fallback goes out, it stays pending. Staff can still approve it as a richer follow-up; the thread shows the acknowledgement before it. The guest may receive two emails in that case, which is acceptable.

### Fallback template

New `sendReturnAcknowledgement(inquiry, ret, propertyName, instructions, branding)` in `resend.js`, built on `sendAppointmentEmail`'s branded frame:

- Subject: `Return request received — <propertyName>`
- Body: greeting by name, "We've received your return request for order **REF**", the lines, the reason if given, then the property's return instructions verbatim (or a neutral "We'll be in touch with next steps." when none are set), then the usual footer.
- Branding: the enquiry's `branding` if the website sent one, else `property.email_branding`, matching how `sendReply` resolves it today.

### Guest-facing wording

Emails and the dashboard say "return", never "event inquiry". `event_type` stays the literal `Return order items` so the existing feeds and the AI see a stable label.

## Dashboard (ota-table-bookings)

### Reply dialog (`event-inquiry-dialogs.ts`)

When `inquiry.return` is set:

- `buildInquiryDetailsHtml` renders a return panel instead of the date/guests/time/restaurant fields and the convert-to-booking button: reference (with the order's contact name), lines as `qty × name`, reason, and a `<select>` of the legal next statuses computed from the transition table above, with the current status shown as a badge.
- Changing the select calls `PUT /api/proshop/returns/:id`, updates the badge and `inquiry.return.status` in place, toasts on failure and reverts the select. The `Inquiry` type gains `return: InquiryReturn | null`.
- `wireBookingFields` is skipped for return enquiries.

General enquiries render as today. No change to `event-inquiries-client.ts` beyond passing the new field through.

### Orders dialog (`shop-client.ts`, `pro-shop.astro`)

- New **Reference** column, first after the date.
- New **Return** button on rows where `payment_status === 'paid'` and `status !== 'cancelled'`. It opens a new `return-dialog`: the order's lines each with a number input `0…returnable_quantity` (from `POST /orders/lookup` called with the order's own reference and email, so the same cap logic serves both paths), a reason textarea, and Submit. Submit posts the staff shape to `POST /api/proshop/returns`, toasts "Return raised — see Enquiries", and closes.
- Lines with `returnable_quantity === 0` are shown disabled with "fully returned".

### Settings (`settings.astro`, `settings-client.ts`)

New **Returns** tab with one textarea, "Return instructions", and a Save button. Loads from `GET /api/property/me`, saves with `PUT /api/property/me { return_instructions }`. Helper text: "Sent to guests when they request a return, and used by AI replies."

## Error handling

- All 4xx bodies are `{ error: string }` matching the rest of the API.
- Lookup and create never distinguish "wrong email" from "no such order".
- A failure after the transaction commits (Ably, AI, fallback email) is logged and does not fail the request; the return and enquiry exist and staff can reply by hand.
- Fallback-email failure is logged with the inquiry id; nothing retries.

## Testing

OTA has no automated test suite for controllers; verification is manual against the local DB with the dashboard and `curl`/MCP, following the repo's convention.

Checklist:

1. Migration applies cleanly to a DB with existing orders; every order gets a unique reference.
2. Lookup: right pair → lines with correct `returnable_quantity`; wrong email, wrong reference, unpaid order → identical 404.
3. Create: cap enforced (buy 3, return 1, then 2 ok, then 1 → 409); duplicate line → 400; enquiry appears in the dashboard feed with the type badge and generated message.
4. First reply: with AI `auto` and a high score → AI email, no fallback. With AI `draft` → fallback email sent, draft still pending in the dialog. With AI `off` → fallback only. With zero tokens → forward to `fallback_email` plus guest acknowledgement.
5. Status: each legal transition succeeds and the panel updates; each illegal one 409s; `received` restores stock on the items.
6. Staff-raised return from the Orders dialog lands in Enquiries with `raised_by = 'staff'`.
7. Settings tab round-trips the instructions and the AI prompt includes them (check the draft text).
8. General enquiries are unaffected: dialog, convert-to-booking, AI drafts.
